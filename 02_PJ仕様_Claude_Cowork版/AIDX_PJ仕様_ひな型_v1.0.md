# AIDX PJ仕様 ひな型（PJ-01準拠フォーマット）v1.0

**このファイルの役割**：全PJ（PJ-01〜25）の仕様書を**同じ形**で書くための"型"です。`〔 〕`で囲った箇所を各PJの内容に置き換えて使います。
**固定ルール**：章立て（管理メタデータ＋①〜⑨）は**固定**。章を増やしたり減らしたりしないこと。埋められない欄は消さず「該当なし」または「要確認」と書きます。
**見本**：PJ-01（議事録）がこの型に沿った記入済み見本です（同梱の定例資料HTML／aidx-docsのPJ-01仕様を参照）。
**基準**：入力の扱いは **v0.4 の考え方**（音声は「文字起こし後のテキスト」で渡す）を標準とします。

作成: Claude Cowork（ai@側）/ 2026-07-31 ／ 想定利用者: 西村・渡部（量産）、PM（レビュー）、品質確認担当（⑤⑥）

## ② 入力（何を・どの形式で・前提）
> 記入ガイド：入力の種類・形式・必須/任意・前提条件を書く。
> **【v0.4の要点・全PJ共通】** 音声を扱うPJは、生の音声を直接AIに渡さない。**必ず「文字起こし後のテキスト」で渡す**（承認済みの文字起こし経路1〜3のいずれかを経由）。この前提を入力欄に明記する。

| 入力 | 形式 | 必須/任意 | 前提・注意 |
|---|---|---|---|
| 〔例：会議の記録〕 | 〔テキスト（文字起こし後）〕 | 必須 | 〔音声は承認済み経路で文字起こし後に投入〕 |
| 〔補助資料〕 | 〔PDF/メモ〕 | 任意 | 〔 〕 |

- 承認済み文字起こし経路（音声を扱う場合）：経路1=M365 Wordトランスクリプト（法人本命）／経路2=ローカルアプリ（Win:Vibe/Buzz、Mac:MacWhisper）／経路3=ブラウザ内Whisper（検証用）

## ④ プロンプト本体（P-0XX）
> 記入ガイド：下の7ブロックを**必ず全部**含める。ブロックの見出しは固定、中身をPJに合わせて書く。他ツール名（GPT/Codex等）は書かない。

```text
# 役割
〔Claude Coworkとして、この案件フォルダで何をする専門アシスタントか。品質確認まで済ませて提示する旨〕

# 入力の受け取り方
〔01_入力/ の対象ファイルの読み込み方、複数ある場合の扱い、AI利用ルールの参照〕

# 絶対ルール
1. 入力にない事実・担当・期限・数値を推測・補完しない。確認できない項目は「要確認」とする。
2. 「意見・提案・検討中」と「正式な決定」を分ける。
3. 固有名詞・金額・日付・数量は原文の表記を維持する。不確かなら「要確認」。
4. 〔このPJ固有の絶対ルールを追加〕
（音声由来のPJは：根拠欄に発言に近い短い引用を添え、照合時に全体を聞き直さずに済むようにする）

# 作業手順
〔入力特定→論点整理→分類→構造化→要確認の抽出→自己監査、の手順を番号付きで〕

# 品質確認（自動実行・監査基準）
〔AIが自分の出力を照合する監査項目。書き換えではなく判定と指摘を出す。自動確定しない旨〕

# 出力形式
〔成果物の章立てと表の型を具体的に。最後に「品質確認結果（自動実行）」を必ず含める〕

# 保存
成果物（全セクション）は「02_出力/」へ保存。同名があれば上書きせず版番号を上げる。
```

## ⑤ 自動QA（品質確認）の設計
> 記入ガイド：AIが自分の出力を自己監査する項目を箇条書き。**最終承認は人**である旨を必ず書く。

- 〔原文と数値・固有名詞が一致しているか〕
- 〔決定と意見が混同されていないか〕
- 〔要確認が適切に残っているか〕
- 判定は「合格候補／要修正／保留」。人の最終承認前であることを明記する。

## 付録：このひな型の使い方（3ステップ）
1. このファイルを複製し、ファイル名を `AIDX_PJ-XX_Claude_Cowork仕様_vX.X.md` にする。
2. `〔 〕` を上から順に埋める。章は固定・増減しない。埋められない欄は「該当なし／要確認」。
3. ⑧自己検証を記入し、`status` を review にしてPMレビューへ。合意で fixed。旧版は保持。
